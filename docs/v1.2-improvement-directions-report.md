## 2 改进方向总览

v1.2 围绕以下五个方向展开，每个方向标注了来源文档、优先级和预估工作量：

`
方向一：检索质量增强（Evidence Gate + 上下文压缩 + 多阶段 Rerank）
方向二：文档理解升级（Canonical Document Model + Contextual Chunking + Index Versioning）
方向三：AI 基础设施健壮性（Token 批量分片 + 性能指标 + Embedding 缓存 + 模型降级通知）
方向四：评测与可观测性（Golden Set + RAGAS 指标 + OTel Trace + 成本仪表板）
方向五：MVP 降级补齐（Redis 缓存 + DB 数据源 + Trace 追踪 + ChunkMetadata assets）
`

## 3 方向一：检索质量增强

### 3.1 EvidenceGatePostProcessor（v1.1 已含，此处补充调优策略）

v1.1 报告已列出此文件。v1.2 补充以下调优维度：

- **精排分布监控**：上线后采集 rerank_score 分布直方图，据此调整 min-rerank-score 阈值
- **通道级闸门**（进阶）：不同检索通道（vector / keyword / graph / web）可配置不同阈值
- **软闸门模式**（可选）：低于阈值不整批丢弃，而是降低权重，交由融合层统一裁决

### 3.2 多阶段 Rerank

**来源**：modern-rag-improvement-roadmap.md §5.2.4

当前 mneme-rag 只有一阶段 Rerank（cross-encoder）。路线图建议三阶段：

| 阶段 | 手段 | 候选量 |
|------|------|--------|
| 召回 | ANN / BM25 / graph | 100-1000 |
| 粗排 | lightweight score（bi-encoder、规则） | 50-100 |
| 精排 | cross-encoder / ColBERT / LLM listwise | 5-20 |

**实施建议**：
1. 在 
ag/retrieval/postprocessor/ 中新增 coarse_ranker.py（bi-encoder 粗排，order=5）
2. 将现有 
erank.py（cross-encoder）设为精排阶段（order=10 不变）
3. 粗排与精排之间加入 EvidenceGate（order=15 不变）
4. 粗排可先以 Noop 实现，后续接入 lightweight model

### 3.3 Query Understanding 策略化

**来源**：modern-rag-improvement-roadmap.md §5.2.5

当前 mneme-rag 的 query rewrite / decompose 是固定管线。建议改为策略路由：

| 策略 | 适用场景 | 备注 |
|------|----------|------|
| Query Rewrite | 术语化、同义词、指代消解 | 已有，保持 |
| Query Decompose | 复合问题（A 和 B）拆分 | 已有，保持 |
| HyDE | 关键词稀疏场景，生成假设答案增强召回 | **新增**，可选开关 |
| Step-back Prompt | 细节问题先抽背景再检索 | **新增**，可选开关 |
| Multi-Query Fusion | 同义改写多次查询，RRF 融合 | **新增**，可选开关 |
| Semantic Router | 判断意图域（KB/SQL/Web），路由到不同通道 | **新增**，替代固定管线 |

**实施建议**：新建 
ag/retrieval/query_policy.py，按配置或 LLM 判断选用策略组合，替代 
ag/engine.py 中的硬编码流程。

### 3.4 ACL 感知检索

**来源**：modern-rag-improvement-roadmap.md §5.2.6

当前 mneme-rag 没有多租户/权限过滤。路线图建议引入 RetrievalSecurityContext：

`python
@dataclass
class RetrievalSecurityContext:
    tenant_id: str
    user_id: str
    roles: tuple[str, ...]
    allowed_kb_ids: tuple[str, ...]
    clearance: str | None
    deny_tags: tuple[str, ...]
`

**实施建议**：
1. 在 
ag/retrieval/schema.py 中新增此 dataclass
2. 在 RetrieveRequest 中增加 security_context 可选字段
3. 在各 channel（vector / keyword / graph）中增加 scalar filter
4. 缓存 key 必须包含 security fingerprint

## 4 方向二：文档理解升级

### 4.1 Canonical Document Model

**来源**：modern-rag-improvement-roadmap.md §5.1

当前 mneme-rag 的 parser 输出纯文本和 block 列表，缺少结构化的中间表示。路线图建议在 ParsedDocument 之上定义统一中间层：

`
CanonicalDocument
  - document_id / tenant_id / source_uri / content_hash
  - layout_tree
    - section
      - heading / paragraph / table / figure / formula
    - page_provenance(page_no, bbox, reading_order)
  - assets(image/table/formula)
  - ocr_confidence
  - acl
  - ingestion_run_id
`

**实施建议**：
1. 在 
ag/ingestion/parser/model.py 中新增 CanonicalDocument dataclass
2. 让各 parser（markdown / pdf / excel / mineru）输出 CanonicalDocument
3. Chunker 消费 CanonicalDocument 而非原始文本
4. 此改动影响面广，建议在 P2 阶段实施

### 4.2 Contextual Chunking

**来源**：modern-rag-improvement-roadmap.md §5.1.3

为每个 chunk 注入文档级上下文信息：

1. **文档摘要**：全局 300-500 token 摘要
2. **章节路径**：如「公司制度 > 薪资 > 年假 > 管理层倍增」
3. **局部语境**：章节标题、前后句子、图片说明、术语定义

**实施建议**：在 
ag/ingestion/splitter/blockaware/packer.py 的 chunk 输出中增加 context_header 字段，值由章节路径 + 文档摘要片段拼接。

### 4.3 Index Versioning 与 Lineage

**来源**：modern-rag-improvement-roadmap.md Phase A

**当前缺口**：文档更新后，旧 chunk / 旧 embedding / 旧图谱节点的清理和溯源链路不完整。

**建议**：
1. 	_knowledge_chunk 增加 mbedding_version、index_version 字段
2. 新增 	_ingestion_run 表记录每次摄取的完整血缘
3. 双写新旧 index，验证后再切换，支持回滚

### 4.4 ChunkMetadata assets 字段补齐

**来源**：chunk-metadata-assets-gap.md

**当前缺口**：ChunkMetadata 缺少 ssets: List[AssetRef] 字段，无法记录 chunk 引用的图片/表格等资源。

**实施建议**：
1. 在 core/llm/schema.py 中新增 AssetRef(url, mime) dataclass
2. ChunkMetadata 增加 ssets 字段
3. 	o_flat_map() 序列化 assets 列表
4. PDF parser / MinerU parser 输出时填充

## 5 方向三：AI 基础设施健壮性

### 5.1 Token 感知 Embedding 批量分片

**来源**：embedding-batching-optimization.md

**当前状态**：openai_style_embedding.py 的 mbed_batch 按条目数分片（SiliconFlow 32 条/批），不感知 token 总量。2 条 3000-token 长文本可能因超 token 限制而 400。

**改进方案**：

| 层级 | 改进 | 优先级 |
|------|------|--------|
| 分片策略 | 从「按条目数」改为「按 token 总量」 | P1 |
| 并行分片 | asyncio.gather 并行发送各片（当前串行 for 循环） | P1 |
| Token 估算 | 使用 TokenCounterService 估算（非精确可行，成本低） | P1 |
| Provider 差异 | max_batch_size() 按 provider 覆写（百炼 10 / 默认 32） | P1 |
| Token 上限 | 每片总 token 上限（如 8192） | P2 |

**实施建议**：
1. BaseEmbeddingClient 增加 max_batch_tokens() 默认返回 0（不限）
2. mbed_batch() 先按 max_batch_size() 分片，再按 max_batch_tokens() 二次切分
3. 用 syncio.gather 替代串行 for 循环

### 5.2 Embedding / Rerank 性能指标

**来源**：rerank-embedding-optimization-report.md

**当前缺口**：无结构化性能指标（延迟 / 吞吐 / 成功率），后续优化缺基线。

**建议指标**：

| 指标 | 采集方式 |
|------|----------|
| latency_p50 / p95 / p99 | 时间戳差值 + 滑动窗口 |
| throughput (requests/s, texts/s) | 计数器 |
| success_rate | 成功 / 失败计数 |
| fallback_rate | fallback 触发次数 / 总请求 |
| cache_hit_rate | Embedding 缓存命中 / 总请求 |
| token_per_request | 每次请求的输入 token 数 |

**实施建议**：在 RoutingExecutor 中注入 metrics collector，用 prometheus_client 或简单 dict counter 输出。

### 5.3 Embedding 结果缓存

**来源**：rerank-embedding-optimization-report.md §P2

**场景**：入库摄取时，同一文档重复摄取或多个 chunk 有相同内容，可命中缓存减少 API 调用。

**建议**：
1. Redis 缓存 key = hash(model_id + text)，TTL 7 天
2. 在 RoutingEmbeddingService.embed() 层面拦截，命中则跳过 API
3. 批量请求时先查缓存，只对 miss 的文本调 API
4. 注意：不同 embedding model 的向量不通用，key 必须包含 model_id

### 5.4 指定模型降级与用户通知

**来源**：model-fallback-strategy.md

**当前状态**：指定 model_id 的请求失败后直接抛异常，不降级也不通知。

**推荐策略**：
1. 指定模型失败后自动降级到候选模型
2. 响应中携带 allback_used: true + original_model 字段
3. 前端展示提示：「指定的模型 X 暂不可用，已切换到模型 Y」
4. 用户可选择「等待原模型」或「接受降级结果」

### 5.5 Rerank 本地降级

**来源**：rerank-embedding-optimization-report.md

**当前状态**：Rerank API 失败时走 NoopRerankClient（保留原始序），但没有本地降级选项。

**建议**：P3 阶段考虑接入本地 cross-encoder（如 bge-reranker-v2-m3，ONNX 格式）作为 API 失败时的降级方案。

### 5.6 CJK Token 计数精度提升

**来源**：cjk-detection-analysis.md

**当前状态**：HeuristicTokenCounterService 使用手动维护的 Unicode 区间列表判断 CJK 字符。Python 缺少 JDK Character.UnicodeBlock.of() 的等价 API。

**建议**：P3 阶段可考虑引入 	iktoken（OpenAI 官方 token 计数库）替代启发式方法，或在当前方案基础上补充遗漏的 Unicode 区间。

## 6 方向四：评测与可观测性

### 6.1 Golden Set 与 RAGAS 评测

**来源**：modern-rag-improvement-roadmap.md Phase A

**当前状态**：mneme-rag 有 valuation/ 目录和 /rag/eval 端点，但缺少标准化的 golden set 和 RAGAS 指标。

**建议**：
1. 构建 100-300 条标注 QA 对（含正确回答、安全拒答、边界场景）
2. 接入 RAGAS 库，采集 faithfulness / context precision / context recall / answer relevancy
3. 每次 prompt / embedding / rerank 修改必须跑回归并对比基线

### 6.2 OpenTelemetry GenAI Trace

**来源**：modern-rag-improvement-roadmap.md Phase A + retrospective-infra-ai-rerank-vlm-token-feishu.md

**当前状态**：mneme-rag 有基础 trace 表（t_rag_trace_run / t_rag_trace_node），但不支持 OTel 标准格式。

**建议**：
1. 引入 OpenTelemetry Python SDK + GenAI semantic conventions
2. 为 LLM 调用 / 工具调用 / 检索调用生成 span
3. 可选接入 Langfuse 或 Arize Phoenix 作为可视化后端
4. span 中包含 cost / token / model / latency 等属性

### 6.3 成本仪表板

**来源**：modern-rag-improvement-roadmap.md §6 Admin UI

**建议**：Dashboard 增加 per-tenant / per-query / per-document 的 token 消耗和 API 成本统计，利用现有 trace 数据聚合。

## 7 方向五：MVP 降级补齐

### 7.1 缓存从内存升级到 Redis

**来源**：a-layer-mvp-gap-report.md §1.1

**当前状态**：三个缓存（AgentPromptCacheManager / QueryTermMappingCacheManager / IntentTreeCacheManager）均为进程内 dict，无可控过期。

**建议**：替换为 CacheManager（Redis 后端），接口不变，实现替换。

### 7.2 数据源从内存占位升级到 DB

**来源**：a-layer-mvp-gap-report.md §1.2

**当前状态**：AgentPromptResolver / QueryTermMappingService / IntentNodeRegistry / ConversationMemoryService 为内存占位或 Noop。

**建议**：
1. AgentPromptResolver → 接入 	_agent_profile + 	_agent_prompt 表
2. QueryTermMappingService → 接入 	_query_term_mapping 表
3. IntentNodeRegistry → 接入 	_intent_node 表（deleted=0, enabled=1）
4. ConversationMemoryService → 接入 Redis / DB（已有 schema）

### 7.3 Trace 追踪与日志卫生

**来源**：a-layer-mvp-gap-report.md §1.3

**当前状态**：无统一 trace 注解，敏感信息无脱敏。

**建议**：
1. 实现 Python 版 @trace_node 装饰器，自动记录模块名 + 耗时 + 输入摘要
2. 实现 log_safe() 工具，对用户消息、API key 等做脱敏
3. 与方向四的 OTel Trace 合并实施

### 7.4 MetadataEnrichmentPostProcessor / KbCollectionProvider 接入 DB

**来源**：a-layer-mvp-gap-report.md §6.2

**当前状态**：KbCollectionProvider 为 StaticKbCollectionProvider（内存注入），MetadataEnrichmentPostProcessor 的数据源为 NoopChunkMetadataResolver。

**建议**：
1. KbCollectionProvider → 查询 	_knowledge_base（deleted=0）
2. ChunkMetadataResolver → 查询 	_knowledge_chunk + 	_knowledge_document 回表

### 7.5 外部依赖接入（LightRAG / ES / You.com）

**来源**：a-layer-mvp-gap-report.md §6.1

**当前状态**：Graph / Keyword / WebSearch channel 均为内存占位实现，未接真实服务。

**建议**：按 Docker Compose 部署 LightRAG + Neo4j 和 Elasticsearch，替换 Memory 实现为真实 HTTP 客户端。You.com Search 接入实际 API key。

## 10 关键判断

modern-rag-improvement-roadmap.md 的核心理念值得沿用：

> **「可观测、强约束、全链路可版本化、可回放追踪」是 v1.2 的主线。**

具体来说：

1. **不做不能评测的优化**：任何 prompt / embedding / rerank 改动必须有 golden set 回归报告
2. **数据有血缘**：Document → Chunk → Embedding → Answer 全链路携带 source / version / tenant / ACL
3. **成本有约束**：每次调用有 token / 延迟预算，Agent 有 max_iterations / budget controller
4. **降级有感知**：模型降级、Rerank 降级、缓存 miss 都要有明确的状态上报和用户提示
